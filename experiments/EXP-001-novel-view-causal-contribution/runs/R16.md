# R16 — Issue Bankruptcy vs. Maintainer Promotion: Which First?

## Framing

The two options are not interchangeable fixes for the same problem, and the question of sequencing turns on identifying the actual causal bottleneck.

- The **stated harm** is that contributors are leaving. The **stated cause** is six-week median PR review time. That is a throughput problem: two maintainers cannot review fast enough.
- The 400 open issues are mostly a **stock** problem — accumulated backlog. Backlog is demoralizing and noisy, but stale issues do not, by themselves, drive contributors away the way an unreviewed PR does. A contributor with an ignored issue shrugs; a contributor with an ignored PR — work they actually did — quits.

Option A (issue bankruptcy + triage rota) reduces the stock but does nothing for review throughput. Worse, it *adds* a standing obligation (the rota) to two people who are already the bottleneck, and the mass-close will generate a wave of "please reopen" traffic and community friction at exactly the moment the project has no capacity to absorb it. Closed issues reopened into an unchanged pipeline just re-accumulate.

Option B (promote three contributors) is the only option that attacks the causal bottleneck: review capacity. It is also the option with lead time — permission design, onboarding, norm-setting — so if it is going to happen at all, it should be *started* first. And it makes Option A land better: three new maintainers can staff the triage rota and absorb the reopen wave, turning bankruptcy from a two-person cleanup spasm into a sustainable process.

## The security objection, taken seriously

"Under a year of activity" in a security-sensitive project is a real concern — supply-chain attacks via patient sock-puppet contributors are documented (the xz/liblzma compromise is the canonical case, and its perpetrator had *more* than a year of history). But the mitigation for that risk is not "never add maintainers"; a two-person project in security-sensitive use is *itself* a security risk (bus factor, review fatigue, rubber-stamping under load). The mitigation is **scoped, graduated trust**:

- Grant the three contributors **triage + review rights**, not the full keyring: no release/signing keys, no security-advisory access, no force-push or CI-secret access.
- Branch protection requiring **one founding-maintainer approval** on merges to protected branches (or at minimum on security-sensitive paths), so new maintainers accelerate review without becoming a sole gate.
- New maintainers clear the easy 80% of the PR queue and run issue triage; the founders' attention concentrates where their trust is irreplaceable.

Under this structure, Option B's risk drops to roughly the risk the project already carries by accepting these contributors' PRs at all — while the throughput gain is immediate.

## Recommendation

**Do Option B first — but in the scoped form above, not as unconditional full promotion.** Announce it, set up the tiered permissions, and let the new maintainers start clearing the PR queue. Then, within a few weeks, do Option A *with* the new maintainers staffing the rota and handling reopens. Both are worth doing; the sequencing matters because A executed by an exhausted two-person team makes things worse, while A executed by a five-person team is routine hygiene.

If the platform or project genuinely cannot tier permissions (all maintainers get release access, no branch protection possible), the calculus flips: do A first as the only safe pressure release, and invest the bought time in building a vetting/graduation path for the three contributors.

Recommendation: Option B first — promote the three contributors with scoped permissions (triage + review, no release/signing or security-advisory access, founding-maintainer approval still required on protected branches); follow with Option A a few weeks later, staffed by the enlarged team.

Confidence: 72

Main reason: Contributor attrition is caused by PR review latency, which only added review capacity fixes; issue bankruptcy leaves the causal bottleneck untouched and adds triage load and reopen-traffic to the two people who are already the constraint, whereas promoting first also supplies the staffing that makes the bankruptcy sustainable.

Condition most likely to change recommendation: If maintainer status cannot be permission-scoped — i.e., promotion necessarily grants release/signing, CI-secret, or security-advisory access with no branch-protection backstop — the security exposure of fast-tracking sub-one-year contributors outweighs the throughput gain, and Option A should go first while a slower vetting path for Option B is built.
